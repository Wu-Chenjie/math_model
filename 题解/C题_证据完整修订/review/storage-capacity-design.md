# 可用储能窗口消融：独立控制设计审查

结论：设计可执行；下列实现条件须在年度运行前落实并用短段验证。本审查不运行年度计算，不预设任何费用或库存结果。

## 实际运行脚本复审补充（优先于下文候选调用链清单）

作者随后明确本轮保留的主模型是 `C题_跨日随机控制/src/run.py`，而非nextgen框架。已独立读取 `revision/storage-study/run_capacity.py`：

- `production.affine_plan.__globals__ is control.__dict__`、`production.execute.__globals__ is control.__dict__` 及MarkovDP类身份检查准确；此实际路径只需更新control的界，不触发下文nextgen/copied-bound问题。
- W=0在调用production.simulate前固定control上下界，并替换下层为LockedInventory，因而上层和实际执行均无可用储能，逻辑正确。
- 各宽度30kWh步长、四机制合同重解、真终点6000、实验独立容量界断言、供需/状态/互斥/费用重算均符合设计。
- 实际时域仍是旧两午夜 `horizon_days=2`，不是固定72小时。容量实验应明确这是保留原主模型的容量消融，不与下一代72小时融合候选混称同配置。

输出父目录已由启动流程创建。独立验证脚本保存所有最大残差、12组总费分解、三对容量差及7日块诊断；另在任务运行期间记录观察时刻的哈希快照，于完工比较producer自报与当前散列。该快照明确不是启动前注入式记录；运行期间不修改producer。它们无需改变控制模型。

以下2节列出的是更广泛nextgen/原生后端复用时的风险清单；本次实际原run路径经上述断言已避开这些额外分支。其余设计解释、零窗口、统计和绘图条件仍适用。

## 1. 实验定义与可解释范围

固定中心库存6000 kWh，令可用库存窗口宽度 W 分别为0、4800、9600 kWh。各组边界分别为 `[6000,6000]`、`[3600,8400]`、`[1200,10800]`。真实初末库存都为6000；效率0.9、母线充放电功率5MW、预测、场景、合同权限、重规划规则和末值公式保持相同，全部合同和电池闭环重新求解。

建议命名“可用储能窗口消融”或“可用容量消融”，不要称额定电池容量分别为0/4800/9600。实际改变的是可调库存范围，6000中心偏置及固定功率仍保留。W=0代表电池没有可调节能量，在本模型中等价于禁止电池充放电；它不是一个物理额定容量为0却储有6000电量的设备模型。

同一精确策略模型下，可用区间嵌套给出最优费用非增关系；实际LP+近似DP+滚动重规划的闭环结果仍须计算，不保证各实测费用随W单调。出现非单调时如实报告，不能换网格或策略追求预设顺序。差额衡量可用储能窗口通过合同与电池联动产生的闭环效果，不是固定合同条件下的纯电池动作收益，不是容量投资经济性（未含设备成本/退化）。

## 2. 必须防止遗漏的容量界

已读 `C题_下一代随机控制/src/control.py`、`nextgen_control.py`、`nextgen_run.py` 及 `cpp/native_planner.py` 的界与调用位置。实际运行若使用打包源码副本，也需在那个确切导入位置核对。

| 位置 | 必要处理 |
|---|---|
| control.EMIN / EMAX | 修改上层legacy LP状态边界、MarkovDP网格与动作区间、execute物理投影，以及潜在prune_cuts域。 |
| nextgen_control.EMIN / EMAX | 它们通过from-import复制，改control模块不会更新此处；非legacy上层、WeightedMarkovDP、minimize_action、M1均引用这组界。必须同步。 |
| nextgen_control.legacy_affine_plan / MarkovDP | 当前主配置走这些旧函数；即使包装新上层，也不可遗漏函数定义模块control的全局界。 |
| nextgen_run.execute别名 | 若只修改control模块全局界，原函数会读更新后的界；若替换execute函数对象，则已有from-import别名须同步替换。其他包装函数同理。 |
| cpp/native_planner.EMIN / EMAX | 如启用原生规划器，它也有独立from-import界，必须同步；若本实验不使用，应在运行日志明确实际后端，避免误认为已覆盖。 |
| nextgen_run物理审计 | 目前末尾仍以1200/10800硬编码检查，无法发现4800组越出3600/8400。须追加本实验真实区间的独立逐段断言。 |

优先采用显式参数或容量专属进程。若暂用模块全局注入，必须每个任务进程独立设置所有界；不能多个线程同时改共享全局。进程池复用worker时，每个任务必须重新设界并在结束恢复，避免W=0污染下一任务。每任务保存所有相关模块实际界、文件路径和源文件散列。

## 3. 零窗口与网格

W=0时上层LP也必须固定每个场景库存为6000；只让下层不动作而仍按9600容量规划，会形成失配基线。保留场景预测与合同重解，库存增量为零，紧急电为净需求减最终合同的正部，弃电由平衡恢复。线性末值变成对合同无影响的常数，不影响最优合同；可以保留评分常数，但不混入现金账单。

W=0跳过DP并令请求恒6000是正确的单点状态实现。不得创建重复库存节点再做差分斜率，这会导致除零。实际执行检查充电、放电为零，库存全部6000，母线平衡成立。

W=4800用161节点、W=9600用321节点，步长均为30kWh，两组均包含6000，且小网格为大网格中间子集。这保持绝对插值分辨率，避免同节点数导致小窗口更精细。不得改变效率或M来补偿容量变化；固定5MW意味着可放能时长随窗口改变，这是设计本身的物理后果。

## 4. 运行前短段闸门

1. 在单个规划节点用三组界求上层，检查所有`scenario_state`而不只检查真实执行状态；4800组必须全部在3600—8400。
2. 验证DP实际网格端点、步长、节点数；W=0确认跳过构造。
3. 选含跨午夜和真实终点的短段，检查每组状态递推、单向动作、功率、合同截止、初末6000与午夜连续。终点可达域应使用实验边界交集。
4. W=9600用同一平台、后端、源码与输入重放一个已有段，核对合同与库存一致。年度9600基准若使用新计算，统一用本实验新轨迹比较；不能静默拼接跨平台旧费用。
5. 改变未来真实数据不应改变当前合同；容量参数在运行前固定，不能根据已知未来误差逐日切换。

容量改变不应改变预测和历史场景；可抽样核对同一原点三组的场景、权重和预测完全一致。因为当前主场景不依赖实际电池库存，此检查具有直接可行性。若后续加入依赖电池状态的场景选择，则“同场景”解释须另行评估。

## 5. 年度结果与库存图的证据要求

- 四机制、三个窗口各自输出完整334日JSON/NPZ或等价逐段轨迹，含日期、配置、费用、原/有效合同、充放电、紧急电、弃电、库存、后端和散列。
- 独立按实际交付价格重算账单，并检查实验自身容量界、状态方程、供需平衡、充放电互斥、5MW功率、跨日连续和真实末库存；不能只沿用原生产审计的1200—10800判据。
- 全年库存图按真实时间绘制。连续向量可取各日最初144个库存点拼接，再追加最后终点，长度48097；避免把每个午夜重复画成额外十分钟或将334日重排成代表日。
- 可画四机制各自全年曲线/日内热图，显示实验实际边界。若归一化，注明是相对可用区间还是固定额定容量；W=0不可除以窗口宽度。
- 费用差、吞吐量、触界时长及峰谷库存等均从输出计算；没有数据的机制或窗口留空/待计算，不能由其他组插值。所有新增结论有明确轨迹来源。

本审查建议在上述短段检查通过后运行完整年度。设计无需新增未来信息或改主模型；它回答可用储能窗口对当前闭环账单与库存使用的作用。
